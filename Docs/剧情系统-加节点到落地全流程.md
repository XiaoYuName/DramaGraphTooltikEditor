# 剧情系统：从「加一个节点」到「宿主跑起来」

两个工程、四层代码、一条单向的数据流。搞乱的原因通常是把"数据"和"表现"混在一起想了——
先记住一句话：

> **编辑器只产出数据，包只定义结构和流程，宿主负责一切"长什么样"。**

---

## 一、全局架构

```
┌─ DarmaViewEditor（编辑器工程）────────────────────────────────┐
│                                                              │
│  Assets/Drama/Editor/Node/*.cs      GraphToolkit 节点          │  ← 策划在图里连的东西
│  Assets/Drama/Editor/Export/*.cs    节点 → 指令 的翻译层        │
│                    │                                          │
│                    │  导出（DramaExportWindow）                │
│                    ▼                                          │
│  drama_{id}.asset                   DramaScript 资产           │  ← 纯数据，只读
│                                                              │
│  Packages/com.lumino.drama.runtime/  ← 包的源码也在这个工程里    │
└──────────────────────────────────────────────────────────────┘
                     │  npm publish → 私服
                     ▼
┌─ AFramework（宿主工程）───────────────────────────────────────┐
│                                                              │
│  com.lumino.drama.runtime           装包                       │
│  Assets/Scripts/XFramework/C#/Drama/ 服务实现 + 调度            │  ← 你写表现
│  Assets/AddressableAssets/.../Drama/ 放 drama_*.asset          │
└──────────────────────────────────────────────────────────────┘
```

### 包内四层（`Packages/com.lumino.drama.runtime/Runtime/`）

| 层 | 内容 | 认识什么 |
|---|---|---|
| `DramaScript.cs` | `DramaScript` + 各 `XxxAction` | 纯数据。只依赖 UnityEngine / Odin(Attributes) / DOTween 的枚举 |
| `Flow/` | `DramaPlayer`、`DramaScriptIndex`、`DramaFlowResult` | 流程语义。**不认识任何具体指令类型** |
| `Handlers/` | 各 `XxxActionHandler` | 认识指令，但只调 `Services/` 里的接口 |
| `Services/` | `IDialogueView` / `IActorStage` / `IDramaScreen` / … | **只有接口，实现在宿主** |

层与层之间是单向的：`Services ← Handlers ← Flow ← Data`。
Handler 永远不会 `new` 一个 MonoBehaviour，Flow 永远不会 `switch (action)`。

## 二、加一个新节点：完整 5 步

以「播放音效」为例（假设还没有这个节点）。

### 第 1 步｜包里加数据类型 —— `DramaScript.cs`

```csharp
/// <summary>播放一次性音效。</summary>
[Serializable]
public sealed class PlaySfxAction : DramaAction
{
    public override string Kind => "播放音效";
    [LabelText("音效ID")] public string SfxId;
    public override string Summary => $"音效 · {SfxId}";
}
```

⚠️ **类名 / 命名空间 / 程序集名一旦定下就不能改。** `[SerializeReference]` 存的是
`{ 类名, 命名空间, 程序集名 }` 三个字符串，改了之后**已导出资产里对应指令会全部变 null，
而且不报错**。要改就得全量重新导出。

### 第 2 步｜编辑器加节点 —— `Assets/Drama/Editor/Node/`

```csharp
[System.Serializable]
[Node("命令/音乐", "Assets/Drama/Assets/Music.png", "播放音效")]
public class PlaySfxNode : DramaNode
{
    public const string SfxID = "sfxID";

    protected override void OnDefinePorts(IPortDefinitionContext context)
    {
        base.OnDefinePorts(context);      // ← 必须调，这行加的是流程进/出端口
        context.AddInputPort<string>(SfxID)
               .WithDisplayName("音效ID")
               .WithCapacity(PortCapacity.Single)
               .Build();
    }
}
```

节点类**不写任何执行逻辑**，它只是一个"填参数的表单"。

### 第 3 步｜写翻译 —— `Export/DramaNodeExporters.cs`

在 `TryExport` 的 switch 里加一个 case，再写对应的静态方法：

```csharp
case PlaySfxNode n:  ExportSfx(n, ctx); return true;

static void ExportSfx(PlaySfxNode n, DramaExportContext ctx)
{
    var id = ctx.Port(n, PlaySfxNode.SfxID, string.Empty);
    if (string.IsNullOrEmpty(id)) ctx.Warn("音效ID 为空", n);
    ctx.Emit(new PlaySfxAction { SfxId = id });
}
```

`DramaExportContext` 给你的工具：

| API | 用途 |
|---|---|
| `ctx.Port<T>(node, portName, fallback)` | 取输入端口的值（会顺着连线求值） |
| `ctx.Option<T>(node, optionName, fallback)` | 取节点选项（下拉框那种） |
| `ctx.EvalLocalized(port)` | 取多语言引用，产出 `LocalizedRef` |
| `ctx.Emit(action)` | 产出一条指令；同一次调用里 Emit 多条会自动串起来 |
| `ctx.Warn / ctx.Error` | 导出诊断，不中断 |

> 翻译**集中在这一个文件**，不散到各节点类里——编辑器类型和运行时类型是两套独立的东西，
> 中间放一层翻译，两边才能各自演进。
> 节点也可以自己实现 `IDramaExportNode` 接管导出（优先级高于 switch），
> 适合那种一个节点要产出好几条指令、逻辑很长的情况。

**忘了写这一步会怎样**：导出时记一条警告，该节点被跳过，但链条不会断——
导出器会顺着它的下游继续找入口，前后节点照样连上。

### 第 4 步｜包里加 Handler —— `Runtime/Handlers/`

先问自己一个问题：**这条指令需要碰"长什么样"的东西吗？**

**不需要**（只用现成的 Service 接口串一串）→ 写进包里，注册到 `DramaDefaultHandlers`：

```csharp
public sealed class PlaySfxActionHandler : DramaSimpleActionHandler<PlaySfxAction>
{
    protected override async UniTask RunAsync(PlaySfxAction a, IDramaContext ctx, CancellationToken ct)
    {
        var clip = await ctx.Assets.LoadSfxAsync(a.SfxId, ct);
        if (clip != null) ctx.Audio.PlaySfx(clip);
    }
}
```

**需要**（要新的表现能力）→ 先在 `Services/` 加接口、在 `IDramaContext` 加槽位，
再写 Handler。判断标准不是"这个功能通用吗"，而是**"结构通用吗"**：

> 全屏转场每个工程画法都不一样，但结构都是"盖上 → 揭开"，
> 所以 `IDramaScreen` 只出 `CoverAsync` / `RevealAsync`，怎么画交给实现。
> —— 同理 `IActorStage` 刻意不认识 Spine。

三种基类按需选：

| 基类 | 适用 |
|---|---|
| `DramaSimpleActionHandler<T>` | 干完活继续往下走（绝大多数） |
| `DramaActionHandler<T>` | 要改流程走向（返回 `Jump` / `Stop` / `Goto`） |
| `IDramaActionHandler` | 极少，一般用不上 |

**注册必须手写**，不要反射扫程序集——IL2CPP 代码裁剪会把没被静态引用的 Handler 裁掉，真机才炸。

### 第 5 步｜宿主实现 Service

只有第 4 步加了新接口时才需要这一步。实现放
`Assets/Scripts/XFramework/C#/Drama/`，然后装配进 `DramaContext`。

| 接口 | 宿主实现 | 状态 |
|---|---|---|
| `IDramaAssetProvider` | `DramaAssetProvider` | ✅ 业务ID → AA Key，接 `AssetsManager` |
| `IDramaLocalization` | `DramaLocalization` | ✅ 接 Unity Localization |
| `IDramaAudio` | `DramaAudio` | ✅ 转发 `AudioManager` |
| `IDramaGameBridge` | `DramaGameBridge` | ✅ 除领任务外都接通了，见下表 |
| `IDramaScreen` | `ScreenActionController` | 🚧 全屏转场 |

装配点只有一处：`DramaDirector` 的构造函数（资源类）+ UI 打开时往 `Director.Context` 塞（表现类）。

### `IDramaGameBridge` 的十四个口子

它是"剧情要回调宿主业务"的杂物袋，加指令时最常动的就是它。

| 方法 | 谁在用 | 宿主怎么落地 | 状态 |
|---|---|---|---|
| `ReceiveTaskAsync` | 「领取任务」 | — | ⚠️ 还是打日志占位 |
| `ChangeGameSceneAsync` | 「游戏场景」 | `GameSceneManager.EnterGameScene` / `OptionGameScene`，盯着转场计数归零才返回 | ✅ |
| `RequestOpenUIOnEnd` | 「UI结束」 | 只记下来，收尾后 `UISystem.OpenUI` | ✅ |
| `RequestStartGuideOnEnd` | 「引导结束」 | 只记下来，收尾后 `TutorialManager.StartTutorial` | ✅ |
| `SetSceneVisibility` | 「场景显隐」 | `GameSceneManager.SetSceneNpcVisible` / `SetDefaultSceneUIVisible` | ✅ |
| `ShowRewardAsync` | 「获取奖励」 | `GameDataManager.GrantReward` + `PopRewardUI`，按模式等 | ✅ |
| `ShowUIAsync` | 「打开界面」 | `UISystem.OpenUI` + 轮询 `isOpen`，按模式等 | ✅ |
| `PlayMinGameAsync` | 「小游戏」 | `CharacterManager.Execute` + `DramaMinGameSession`，等玩家点掉成功界面 | ✅ |
| `UnlockSystemFunction` | 「解锁」(系统功能) | `FunctionUnlockManager.UnlockSystemFunction`，进存档 | ✅ |
| `UnlockCharacterFunction` | 「解锁」(角色功能) | 同上，按角色 + 功能位攒 | ✅ |
| `UnlockMap` | 「解锁」(地图) | 同上，`小地图ID = -1` 表示大地图入口本身 | ✅ |
| `SetSystemFunctionVisible` | 「系统功能显隐」 | `FunctionUnlockManager`，**运行时状态、不进存档** | ✅ |
| `SetCharacterFunctionVisible` | 「人物功能显隐」 | 同上 | ✅ |
| `SetMapVisible` | 「地图显隐」 | 同上 | ✅ |

**收 `mode` 的那两个方法是一类**（和 `IDialogueView.ShowLineAsync` 同一个路子）：
包只负责把播放模式交出去，"正常模式等玩家关、自动亮一会儿、跳过立刻收"这套节奏由宿主定，
这一层不该知道界面长什么样。等待手段也各按各的来 —— 奖励弹窗有关闭回调，
而「打开界面」能开任意界面、不可能给每个界面加回调，只能轮询 `isOpen`。

**有副作用的指令必须自己拦读档恢复**：`Restoring` 是静默重放，整段剧情会重走一遍。
发奖励、领任务、弹界面都在 Handler 里拦掉了 —— 不拦的话玩家每读一次档就白拿一份奖励、
重领一次任务。跳过（`Skip`）**不拦**：那是"结果照旧、过程不看"，玩家人在现场。

**反过来，解锁 / 功能显隐那六条刻意都不拦 `Restoring`**：解锁是幂等的集合写入，重放一遍结果一样；
而显隐意图**根本不在存档里**，正是靠重放才能恢复到退出时的样子 —— 拦掉的话读档之后
引导藏起来的按钮会全冒出来。判断标准不是"有没有副作用"，而是**"重放一遍会不会多给玩家一份东西"**。

三条容易写错的契约：

- **两个 `RequestXxxOnEnd` 只能"记下来"，不能当场执行。** 调用发生在剧情还没收尾时，
  当场开的界面会被随后的"关剧情面板 + 还原进剧情前的界面"盖掉；引导更是会指到一个还没回来的按钮上。
  真正执行在 `DramaManager.TeardownDramaRuntime` 的末尾，顺序是
  `ResumeSceneContent` → `RestoreUI` → `OpenEndUIIfRequested` → `StartEndGuideIfRequested`。
- **`SetSceneVisibility` 收到的是一个持续"意图"，不是一次性动作。** 剧情中途切场景会新建
  `SceneController`（重新生成一批 NPC）并重新开场景默认UI，执行一次就完是拦不住的 ——
  宿主把它存在 `GameSceneManager` 上，每次场景就绪时重新应用一遍。
  正因为如此，**「游戏场景」节点上不需要再带一份显隐参数**：把「场景显隐」摆在切场景<b>前面</b>
  就行，新场景一建好就按新意图生成，不会先冒出来再被收掉。
- **进剧情时宿主默认把 NPC 和场景默认UI 都收起来**（剧情要独占屏幕），收尾原样还回去。
  所以剧本里只在"想露出来"时才需要摆「场景显隐」。

## 四、运行时流程

```
DramaManager.StartDramaRuntime(script)
  └─ DramaDirector.PlayAsync(script, ct)
       ├─ EnsureServices()                   表现层服务缺了直接报错，不播
       ├─ handlers.FindMissing(script)       缺 Handler 直接报错，不播
       ├─ PreloadAsync(DramaAssetKeys.Collect(script))
       │     多语言表预热 + 立绘/背景/BGM 批量加载
       ├─ player.PlayAsync(script, context, ct)
       │     按 Next 的串行/并行语义驱动 → Handler → Service
       ├─ ReleaseSegment()                   收动画 → 清舞台 → 清遮罩 → 还资源
       └─ Goto? 加载 drama_{id}.asset 接着循环 : 结束
```

几条容易踩的：

- **`Next.Length` 决定串并行**：0=结束，1=串行，>1=并行。并行用结构化 fork-join，
  各分支跑到汇合点就停，`WhenAll` 等齐再继续。**不要**拿 `InboundCount` 去等入边，
  图里有选项分支时未选的那条永远不到，会死锁。
- **换剧本是 while 循环不是递归**，连播 N 段栈也是平的。
- **收尾顺序不能反**：先 `CompleteAllTweens` 再 `ReleaseAll`，反了 Tween 会去动已销毁的 Transform。
- **资源一进一出**：`AssetsManager` 按调用次数记引用，所以 `DramaAssetProvider`
  缓存的是**加载任务**（`Preserve()` 过的），保证每个 Key 只 Load 一次、`ReleaseAll` 一次还清。

## 五、发版与联调

改了包之后宿主不会自动看到，要走一遍：

```
DarmaViewEditor 里 DramaPackageReleaseWindow
  → Bump Patch → npm publish（私服 http://192.168.10.226:4873）
AFramework
  → Package Manager 右下角刷新 → Version History 选新版
    （或直接改 Packages/manifest.json 的版本号）
```

> 没有 Update 按钮 = 已经是最新版了。Unity 6 的版本切换在 **Version History** 页签，
> 不在 Manage 下拉里。⚠ Signature Missing 是私服包的正常现象，忽略。

**接口还在反复调的阶段**，可以临时把宿主 manifest 改成本地路径，两边即时同步：

```jsonc
"com.lumino.drama.runtime": "file:../../GitLab/Darma/DarmaViewEditor/Packages/com.lumino.drama.runtime"
```

⚠️ 这个文件在 git 里，队友拉到会因为路径不存在而炸，只适合本机调，定稳了切回版本号。

**给 Service 接口加方法是破坏性改动**：宿主装的还是老包，接口上没有那个方法，
所以"先发包再改宿主"看起来是唯一顺序。但有个省事的做法 ——
**宿主那边可以先把实现写完**：多几个不匹配任何接口成员的公开方法照样编译得过，
包一到位它们自动满足新接口。这样发包之后只剩"改 manifest 版本号 + 编译"两步，
不用在包没到位的时候留一堆半截代码。

反过来，**删成员 / 改签名**没有这种便利，那种改动只能先在宿主把引用摘干净。

## 六、排错速查

| 现象 | 原因 |
|---|---|
| 资产变 Missing Script | 两个工程的 `DramaScript.cs` GUID 不一致（手工拷 .cs 了，必须用包共享） |
| 指令莫名变 null，不报错 | 改过类名 / 命名空间 / asmdef 名 |
| `用到了没注册 Handler 的指令：X` | 第 4 步没做。这是预检在正常工作，不是崩溃 |
| `表现层服务还没装配：X` | 第 5 步没做，或 UI 没打开就播 |
| 导出后某节点没产出指令 | 第 3 步没做，看导出窗口的警告列表 |
| 端口名打错 / 导出映射漏接 | **编译不出来**，只有实跑导出才看得见。加完节点建议：建临时图 → 摆节点 → `graph.Connect` 串起来 → 反射调 `DramaExporter.Export` → 打印 `Actions`，用完删图 |
| 切场景后 NPC / 场景默认UI 又冒出来 | 把显隐当成一次性动作做了。它是持续意图，见「`IDramaGameBridge` 的十三个口子」 |
| 对话记录空白 / 读档恢复不了剧情 | 剧本身份记成了 `script.DramaId`（剧情图「进入」节点填的），那个 ID **不参与加载**、填错也照播。身份必须用**加载它用的配置表 ID**，见 `DramaDirector.ResolveDramaId` |
| Rider 补全不带父接口注释 | 宿主没给 Registry 包生成 csproj：Preferences → External Tools → 勾 Registry packages |
